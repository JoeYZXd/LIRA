# 聊天逐句明细与候选确认阻塞修复

## 实际故障

板端会话 `772546ec6cd5462ba4b5d6b852c4ca6c` 有五轮记录。第 2 轮查档最高分 0.635235，次高分 0.132524，自动识别门槛 0.80，候选下限 0.50。匹配证据已经入库，但没有人工反馈。

随后两句的连续性分数为 0.669997 和 0.670977。此前 `_observe` 只对 recognized 使用 0.65 的连续性规则，collecting 仍用采集分段的 0.73 门槛。这使已经有候选的说话者进入 challenger；`context()` 隐藏候选，`IdentityConfirmation.request()` 拒绝在疑似换人时发起确认。结果是用户问身份时也得不到候选问题。

修复让有候选但尚未确认的声音沿用既有连续性规则和加权判断，允许约 0.67 的稳定波动继续累计。未修改声纹库的 0.80 自动认人门槛、0.10 分差或任何模板。明确不同的声音仍进入多段换人核对，不能因候选存在而直接认定身份。

这次五轮聊天没有自动关联到成员。豆包读取旧聊天时用了“这台设备上次聊到”的表述；已有人工关联仍停留在原来选定的旧会话，没有被搬到本次会话。

## 逐句数据

“聊天记录”中，用户发言下有“用户明细”，助手回复下有“小鹿明细”，默认均折叠。

- 用户明细：转写原文及接口转写事件、本轮查档排序、声纹门槛和分差、拒绝原因、连续性单段/加权分数及门槛、累计时长、排队/跳过/质量处理状态、人工反馈。
- 小鹿明细：会话配置引用、LIRA 实际发送的身份上下文、工具调用参数及结果、接口回执、豆包返回的文本及控制消息、记录的人工关联归属。
- 声纹相似度与转写置信度分开；本地不计算转写置信度，若接口提供则保留在原始转写事件中。
- 已发送、接口已确认、模型实际采用是不同状态。只能展示本地发送与接口返回，不能声称拥有云端内部完整上下文或推理。
- 识别/口头确认身份属于会话观察结果，不自动改写“人工关联的个人记忆归属”。导出 JSON 包含两类数据与关联关系。

`voice_history_turns.turn_number` 为会话内稳定轮号，`voice_history_diagnostics` 以会话及轮号关联事件。身份状态重置或异步队列跳过后仍使用归档轮号，防止把迟到的声纹结果挂到下一句。旧表迁移按每个会话原有记录顺序补轮号，既有 `identity_match_events` 可直接挂回旧聊天。

## 边界

从启用后开始采集原始接口明细。此前只保存过的匹配证据可以展示，未保存的接口内容标明缺失，不推测补造。会话初始化配置在连接前建立归档后记录；新的会话上下文只引用当时已经发送的配置。

发送成功后记录控制消息；PCM 与流式 delta 不入库。API Key、认证头、反馈凭据及 JSON 字符串内部的敏感字段在入库前脱敏。最多保留 4000 条控制事件，单条最多 64KB，超过时明确截断；更早明细可能被清理。诊断写入失败不终止语音传输。登录和隐私联锁沿用聊天记录接口。

## 验证

针对实际分数的回归用例先复现了第二次查档无法继续的问题，修复后可继续查档并发起人工确认，仍不会自动认人。测试覆盖晚完成的识别归属、身份重置后的轮号、旧记录迁移、上下文与实际返回留存、嵌套密钥脱敏、工具 schema 保留、导出归属及隐私模式。

部署前保留了板端数据库快照及代码回滚文件。上线后以只读检查核实：旧五轮原文和分数可读，归属仍未关联，旧接口内容未被补造，声纹模板与部署前逐字节一致。

真实云端验收还发现了一个工具衔接问题：用户已明确纠正姓名时，模型有时只调用 `request_identity_confirmation`，没有继续调用提交工具，并重复问旧姓名。确认工具现会校验已发生的明确发言并直接提交反馈；若用户已经回答过候选问题，再次读取此工具也能完成校验保存，不依赖模型补调一次。未明确表达的发言仍不允许更新身份。

最终通过 189 项后端测试、7 项相关浏览器测试。隔离真实豆包会话完成了候选询问、口头确认、个人记忆、纠正姓名和设备历史查询五轮；确认 `user_confirmed` / `user_corrected` 来源、持久化标签、逐轮转写/声纹/控制消息、初始化上下文及脱敏均正常。测试不使用硬件麦克风或扬声器，不触碰正式档案。期间误按电源键造成一次关机；重新开机后核对旧聊天、模板及部署文件均保持一致，LIRA 自动恢复运行。

## 普通聊天主动确认与候选保持修复

随后对真实聊天的检查证明，上述验收首轮显式询问身份，尚未覆盖普通聊天：会话 `16d23520bf8245ecac23498e3d8baf04` 曾出现 0.6316、0.7136、0.6340 的候选，却一直未发起确认；短句连续性分数 0.6485、加权 0.7466 时，单个 challenger 又隐藏了候选。不能将提示词或 `session.updated` 回执视为普通聊天已闭环的证据。

本次改由本地安排确认，不再把问题搭载到连续性辅助工具结果中：正常回复结束、物理播报及尾音释放后，再等待至少 0.5 秒空隙。候选尚未询问、无录入任务且未有持续换人证据时，通过官方 3.0 JSON 协议 `speech_text_buffer.commit` 播放固定问题。用户新开口、唤醒打断、关闭会话或开启隐私会取消等待。问题未完成不接受反馈；完成后将问题作为 assistant 历史加入云端，聊天记录追加问题而保留原回答，不伪造用户轮次或 tool call_id。

本地候选允许单句波动，声音可疑段单独隔离，不直接混入旧累计。最近六个连续性分数按有效语音时长加权，每窗权重限制为 1–5 秒；候选暂停确认需至少两段可疑声音、累计至少 4 秒，且加权均值低于 0.65。真正切换声音轨道仍需满足原有连续段数/时长、可疑原音重新提取及一致性检查，同时要求加权证据支持变化。自动认人的 0.80 门槛、0.10 分差、候选下限 0.50 及声纹模板保持原策略。

主动问题之后紧接着的明确确认、否认或自我纠正由本地校验并保存，随后发布带 `user_confirmed` / `user_corrected` 来源的身份上下文。问题未回答时，后续另一轮的“是的”不会被套到旧身份问题上；假设性的“如果我是李四呢”不能直接标注。已确认后明确纠正姓名也可本地保存。口头确认不等于声纹验证，不自动绑定聊天为个人记忆。

新增逐轮事件 `identity.confirmation_scheduled`、`identity.confirmation_delivered`、`identity.confirmation_failed`、`identity.feedback_saved`；声纹进度中增加 `candidate_change_pending`，并保留单段及加权分数。确认与纠正原始反馈全部保留；标签汇总只取每条匹配事件的最新反馈，因此同一事件先确认后纠正时，汇总只显示 corrected，原来的 confirmed 行仍可查。

通过 196 项相关后端测试，最后对调度收尾重跑 52 项确认/会话测试。部署后使用隔离数据库、合成语音及真实豆包连接完成五轮验收：普通公园话题首轮未调用任何身份工具，本地自动在原回答后播出候选问题；下一轮确认张三并读取其人工关联的番茄记忆，随后纠正为李四；未识别时仅以“这台设备上次聊到”读取向日葵历史。另一个 SQLite 连接重新读到 confirmed、corrected 两条反馈；第 2/4 轮实际发送的上下文分别包含正确来源，第 4 轮包含李四，均收到接口回执；模型身份工具和实际回复跟随更新。五轮归档没有新增人工关联，测试模板版本未改。此验收验证协议与数据链路，不测真人声纹准确率或物理扬声器效果。
