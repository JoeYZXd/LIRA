LIRA → 家庭局域网 → 客厅电视显示终端
N1 已确认的目标与交互规则已确认

目标设备暂按 2017 款小米电视 4、65 英寸分体版研究；用户已确认分体套装，尚未从设备读取精确型号及系统版本。电视与 LIRA 在同一家庭网络。

R1：展示 LIRA 生成的大字、图片、阅读原文和回答页面；用户优先选择此用途，而非实时桌面镜像或摄像头直播。

R2：电视待机时允许自动开启并展示；电视正在使用时先语音询问，明确同意后才切换。R3：展示结束后，仅本次由 LIRA 开启的电视可自动关闭。

R4：允许一次性安装 LIRA 电视应用；完成配置后日常无需手动打开应用。上述均为 user-directed；自动抢占正在观看的节目不符合用户选择。研究阶段不宣称已经具备全自动能力。

N2 硬件与平台证据已核实／待实机

小米官方分体版参数列出 65 英寸屏幕、独立主机、低音炮及两个后置环绕音箱，并标注该列为 3GB 内存、32GB 存储、双频 Wi-Fi、以太网及蓝牙。它与后来的 65 英寸一体机是不同研究对象。[S1]

官方参数未证明当前固件的 Android API 级别、WebView 版本、网络待机、Wake-on-LAN、ADB 开放方式或第三方自启动能力。不能以购买年份推断当前 Android 版本，也不能把同品牌新电视的能力套用到这台设备。

分体结构意味着主机存活、系统 interactive、逻辑 Display 状态与物理屏幕亮灭可能不完全一致。任何状态信号必须与实机屏幕观察对照，主机在线不能单独证明正在观看或正在待机。

N3 三个候选路径与推荐建议

方案 A：电视原生接收应用 + 局域网控制。应用负责展示和回报自身状态，控制通道负责启动展示、唤醒与待机。优点是展示灵活、可持续更新；未知点集中在老固件的控制和后台能力。推荐优先验证此路径。

方案 B：沿用电视内置 DLNA 等媒体投送。适合图片或预生成媒体，但动态阅读高亮、回答增量更新、会话退出与状态回执都需要额外约束；小米通用投屏介绍不能证明本机可自动切换和关机。[S2]

方案 C：常在线外接接收器，经 HDMI-CEC 控制电视。可以绕过电视应用后台限制，但增加硬件，并且 CEC 也必须实机验证；Android 的 CEC 文档说明 One Touch Play 可尝试唤醒电视并成为活动源，不能据此认定本机支持全部行为。[S7]

优先 A；B 只作受限媒体备用，C 只在实机否定 A 后评估。当前不要求购买设备、不采用刷机或 root 作为前提。

N4 推荐架构：内容与控制分离技术研究建议

LIRA 负责内容整理、语音确认和展示会话；电视接收端负责大字、图片、阅读原文和回答卡片。应用安装在分体电视运行 MIUI 的主机一侧；无需改动低音炮和环绕音箱。安装位置最终由设备包管理信息确认。

建议首版采用原生 Android 视图与图片控件，减少依赖老旧 WebView。电视按模板渲染结构化内容，而非执行模型生成的任意 HTML 或脚本。LIRA 现有 FastAPI 服务可作为局域网接口的扩展起点；不直接暴露管理后台给电视。

电视主动连接 LIRA，使用带配对凭据的 WebSocket 接收会话命令与内容更新，图片通过带授权的 HTTP 资源获取。每次更新带会话编号和版本；重连只恢复仍有效的会话，过期页面不能重新弹出。具体接口尚未冻结。

首版建议声音继续由 LIRA 播放，电视负责视觉内容，避免重复播报和新的回声路径；这是建议，用户尚未决定音频是否切到电视音响。

N5 控制通道及 Android 权限边界关键待验证

普通第三方应用不能凭安装自动获得系统电源控制权限。AOSP 将低级电源管理 DEVICE_POWER 标为非第三方应用权限；本机老固件的具体实现还要核对。[S6]

更新后的优先次序：先核对用户已可用的米家开机路径及 MIUI 本机控制，再实测应用能否后台接收消息、完成一次性配置后开机恢复连接、得到授权后进入前台。BOOT_COMPLETED、前台服务和保活机制都只是实现候选，不代表固件必然允许，更不应持续持有 CPU 锁阻止正常待机。[S4]

若米家／MIUI 路径不能覆盖应用启动和状态读取，再验证设备允许的局域网 ADB：读取状态、显式启动 LIRA Activity，并测试明确的 WAKEUP / SLEEP 语义。Android 提供这些键码，但 shell 注入在本机是否生效必须实测，不能把 POWER 开关切换键当成明确开／关。[S3][S8]

老设备不能假设支持 Android 11 的二维码无线调试。Android 通用文档的旧版网络 ADB 方式包含初始 USB 步骤；小米电视是否提供设置内直接开启网络 ADB、是否有可用调试接口、配对是否重启后保持，均未确认。不能假设电视普通 USB-A 插口可作 adb 设备连接。[S3]

如果固件不能提供适用 ADB，可评估小米本机遥控接口或现有 BroadLink 红外控制；补充研究发现 Home Assistant 的 Xiaomi TV 集成与社区 MIoT 实现可作为协议线索，但不构成本机兼容证明；详见 N13。红外码必须单独学习和验证；蓝牙遥控器按键不等于存在可学习的红外码。

若红外只有开关切换码且没有可靠状态，不能实现无歧义自动开关；此组合不满足本次全自动验收。网络、蓝牙和红外只是候选能力，不承诺任何一个必然可用。

N6 状态判断和开机归属建议规则

建议维护：已确认待机、已开启且非 LIRA 展示、正在展示、状态未知。使用最新状态和采集时间；超时、应用断连或 ping 失败统一进入未知，不等同待机。

Android 官方指出 isInteractive 不直接等价屏幕亮灭，建议读取 Display.getState；分体电视仍需验证该逻辑状态是否反映实际面板。结合应用前后台、Display 状态和可用控制通道，而非依靠一个布尔值。[S5]

只有取得可信待机证据、发出本次开机请求并确认屏幕开启后，才记录本次开机归属。原本已开启的电视不取得关机资格；证据不足的开机不冒认归属。

电视已开启且不在本次展示中时，即使没有证据表明正在播视频，也按有人使用处理并询问。这样不需要监视家人在看什么节目。

确认应绑定设备、本次内容和时效；拒绝、沉默或超时均不切换。真正切换前再次读取状态，避免询问期间电视状态变化。未知状态先询问或说明无法确认，不能套用待机自动开启规则。

N7 展示退出、接管与故障建议／有未决项

家人按返回、主页或切换到其他输入源时，建议结束本次展示并撤销自动关机资格；只有应用自身退出证据时不能声称已检测所有 HDMI 输入切换，需验证对应信号。失焦但原因不明时先放弃自动关机，避免覆盖用户接管。

展示结束时，若电视由本次 LIRA 开启、仍在本次展示、状态新鲜且没有接管证据，才发送待机请求。发送成功与面板进入待机分别记录；不能只因命令返回成功就宣称已关电视。这里的关闭指待机，不是切断市电。

原本开启的电视只退出 LIRA 展示，不关电视。建议返回之前的界面；但能否恢复第三方视频播放位置或 HDMI 来源尚无证据，首版不能承诺无缝续播。

展示失败或断网时继续保留 LIRA 的语音功能；过期会话不得自动重弹。LIRA 重启后不根据旧记录补发关机；清空待确认授权，重新核对状态。

未决 U1：什么事件算展示结束，以及读完后是否短暂保留画面，尚未向用户确定。建议允许“结束展示／不用电视了”明确退出，并把内容结束与会话结束分开。未决 U2：用户接管后撤销自动关机、U3：退出后返回原界面的能力与降级，尚需确认或实测。

N8 内容范围与本地配对建议

建议首批模板覆盖：大字回答、图片加说明、分段阅读原文与当前段高亮。电视可独立调字号、行距和对比度；复杂排版与实时镜像暂不纳入当前目标。画面设计和字号参数尚未选定。

自动展示的触发条件尚未冻结：用户明确说“放到电视上”可作为确定入口，LIRA 主动判断何时有必要展示仍需明确规则，不能把所有语音回答都自动开电视当作已确认需求。

首次由家人安装应用并进行配对，保存设备身份和撤销入口；连接需鉴权。内容只授权给已配对终端；日志不记录阅读正文、凭据或模型生成的私人内容。隐私模式及会话过期应清除电视画面和临时缓存，此为建议，需要结合现有隐私合同确定最终行为。

若采用 ADB，只针对已授权设备保留所需控制能力，并限制可访问网络范围。不能把明文广播的任意启动服务当成应用配对通道；不把 ADB 扫描和命令执行权限交给模型。

N9 与当前 LIRA 的衔接证据代码已读取

device/lira/hal/mock/display.py 的 MockDisplay 只将 show/clear 保存到内存；device/lira/main.py 的设备装配仍使用 MockDisplay。现有 Display 接口是文字 show/clear，不能直接承载完整电视会话。

device/lira/ui/app.py 已有本地 FastAPI 应用与隐私状态注入；device/pyproject.toml 的 ui 可选组包含 FastAPI、uvicorn 和 httpx，audio/sync 可选组含 websockets。可扩展现有服务，但需明确安装依赖，不假设所有可选包都已部署。

device/lira/infrared_voice.py 对控制成功明确返回 sent，并说明红外是单向通信；device/lira/appliances/ir.py 有设备启用、已学习码和高危确认检查。复用红外时保留这些检查；自动展示授权应由新的确定性策略执行，不能随意放宽现有“用户明确要求遥控”工具的限制。

初始研究时本机已安装 adb，adb devices -l 返回空列表。r4 已通过用户提供的 IP 取得电视 6095 端口 HTTP 响应，尚未建立 ADB 连接；详见 N14。未向电视发出开关、安装或切换指令，也未修改产品运行代码。

N10 实机验证顺序及通过门槛尚未执行

V1：电视开启时读取精确型号、Android/API、固件版本、可安装 APK 能力和网络地址；确认开机后及重启后能重新连接。必须区分原版分体主机与更换后的主机。

V2：对照物理屏幕验证开启、待机、主机在线但屏幕关闭、HDMI 输入以及断网时的状态报告；待机 1 分钟、30 分钟及隔夜分别测试可达性。分体设备主机和屏幕一起观察。

V3：安装最小接收端，验证后台消息、前台启动、重启恢复、断网重连、后台进程被回收后的恢复；期间不抢占正在播放的节目。应用被用户强制停止是单列的恢复场景，不能由普通自启动承诺自动恢复。

V4：在电视空闲且可观察时分别验证明确唤醒、进入展示、明确待机的通道；记录命令结果与屏幕实际结果。若只有 POWER 切换键，标记受限，不进行盲目重试。

V5：覆盖待机自动展示、已开机同意／拒绝／无回答、等待确认时状态变化、LIRA 开机后正常结束、原已开机展示后结束、遥控器接管、断网、双方重启、旧消息重放。家人正在观看时绝不未经同意切换或关机。

V6：建议通过门槛为上述核心开关与展示流程各连续成功 10 次，并单列隔夜待机和重启恢复；10 次只是首轮验证门槛建议，不是已取得的可靠性数据。全自动能力只有 V1–V5 关键项验证后才可启用。

N11 研究结论与下一步输入研究结论

推荐先验证现有米家／MIUI 唤醒路径，再实现“原生电视接收端 + LIRA 局域网展示会话 + 能力探测后的控制适配”；ADB 降为补充控制候选。应用展示部分有明确工程路径；待机唤醒、精确面板状态、自动前台和自动待机仍是实机门槛。

用户已提供电视 IP：192.168.3.25，已完成第一轮只读探测，见 N14。下一步核对探测时的实际屏幕状态；若后续需要 ADB，且现有设置提供 ADB／远程调试选项，再进行一次性启用及电视端授权。

获取地址后先做只读识别和状态探测，再按 V1–V6 做可观察的能力测试。若无适用网络调试入口，改走最小 APK 的一次性安装与能力报告，而非假设默认 5555 端口开放。

当前 readiness 为 research-draft；没有冻结完整产品合同或实施单元。尚未解决的问题包括 U1–U3、主动展示触发规则、音频归属及本机控制通道。后续计划继续丰富原 HTML/Markdown 文件对，不另建嵌套脑图。

N13 米家已可开机：新证据与验证次序用户实测已确认／接入方式待验证

用户已确认：电视已绑定米家应用，且手机使用移动数据也能远程打开电视。这证明当前配置下的开机路径不依赖手机直接连接家庭 Wi-Fi 或电视蓝牙，具备跨互联网远程控制能力；但尚未验证米家能否读准确电源状态、关机或启动任意应用，也未证明 LIRA 已能调用。

更新后的方案优先验证米家／MIUI 原有控制能力，电视接收应用仍负责内容展示。若开机经云端完成，则云端只承担控制候选，正文和图片仍可在家庭局域网传输；断开互联网时是否仍可自动开机要单独验证，不宣称新增电视能力离线可用。

移动数据开机验证已经由用户完成，不再重复要求测试。现阶段优先核对米家中的设备身份及其暴露的远程控制能力；电视是否直接连云端、是否由家庭网关或其他设备中转仍未知，不能仅凭该结果认定具体 MIoT 协议、OAuth 接口或网络待机实现。LIRA 本轮没有发送开机指令。

研究依据 S9：Home Assistant 官方 Xiaomi TV 文档明确针对 MIUI 电视，支持局域网发现，描述休眠／唤醒；同时其 IoT class 是 Assumed State，不能直接拿其推定状态作为“正在使用时先询问”的可靠依据。该集成是兼容性线索，不代表需要为 LIRA 部署 Home Assistant，也不证明本台电视适配。https://www.home-assistant.io/integrations/xiaomi_tv/

N16 待机连接与唤醒测试米家已恢复／ADB 重连失败

用户明确授权暂时关闭再打开电视，测试待机后 ADB 连通及自动唤醒。对 192.168.3.25:5555 执行 adb shell input keyevent 223（SLEEP）成功返回。约五秒后 get-state 报 device offline，无法取得待机后的 dumpsys power 内容；未由用户目视确认物理面板状态，因此结论限定为发出待机命令后连接丢失。

随后 TCP 5555、6095 连接各两秒超时，adb connect 在八秒限时内未成功。该次试验证明当前待机路径下不能依靠仍存活的 ADB 发送 WAKEUP；没有执行成功的 ADB 唤醒，也不能推导所有待机模式、网线连接或网络设置下都无法唤醒。

尝试查询本机邻居／ARP 缓存以寻找目标电视的 MAC 地址，未获得可用条目。因此没有发送 Wake-on-LAN 数据包，WOL 仍属于未测试能力。当前没有米家账号授权或可调用的远程控制接口，无法把用户已验证的米家开机能力直接用于恢复。

用户已确认通过米家 App 将电视打开。恢复后 5555 和 6095 端口可连接，isalive 返回 HTTP 200/success 及相同 platform=618、build=2312。ADB 初次保留 offline，显式断开目标再连接仍超时；另启独立 5038 端口的 ADB 服务重试，结果同样 offline，随后已停止该测试服务。因此本轮未验证授权是否保留、无法读取恢复后的 ON 状态或网卡 MAC；不能将本轮记录为自动开关闭环成功。

对方案的影响：目前需要独立于待机 ADB 的唤醒通道，米家远程开机仍是已知由用户成功使用的路径；ADB 可作为开机后的应用控制与状态读取通道。自动唤醒尚未接通，电视待机时离线仍不得自动等同于物理待机状态。

补充网络条件：当前开发机到电视的路由源地址为 192.168.101.24，电视为 192.168.3.25；二者处于不同的常见 /24 地址段。尚未读取实际掩码及网关拓扑，不能认定同一广播域。普通本地广播 WOL 的可达性需另行核实，这也可能解释开发机 ARP 缓存没有电视条目，不能据此判定电视没有 MAC 地址。

当前可确定：米家能恢复电视服务，但现有环境中 ADB 未自动恢复。端口开放不等于 ADB 握手成功；独立电脑端 ADB 服务也失败，降低了仅是旧客户端连接缓存问题的可能，但尚不能确定电视 adbd、网络路径或授权的具体原因。下一步需要用户关闭再开启电视 ADB 调试，让服务重新初始化；若弹出授权提示再允许。

N18 网络唤醒与诊断应用限时恢复测试待恢复

状态：当前网络路径下未唤醒／等待米家恢复后检查 ADB 握手。

用户授权继续待机和唤醒测试，并已允许安装临时诊断应用 org.lira.wakeprobe（LIRA Wake Diagnostic）。应用兼容 API 23，记录屏幕事件与状态，提供十分钟限时 UDP 接收，并可安排一次 90 秒恢复闹钟；未接入正式 LIRA 功能。源代码和测试记录保存在 tmp/tv-wake-probe。

亮屏时诊断应用报告 interactive=true、display=2。电脑发往 192.168.3.25 的 UDP 单播到达，电视记录来源为 192.168.3.7；同期发往 192.168.3.255 的定向广播未见接收记录。电脑实际路由源为 192.168.101.24，经网关 192.168.101.1 访问电视。因此存在地址转换迹象，当前路径不是直接同广播域访问；单次未收到广播不能定位具体过滤设备。

安排 90 秒恢复闹钟后，执行 SLEEP 成功返回；约两秒后 TCP 5555、6095 都不可达。在约第 15 秒向电视 IP、约第 40 秒向其子网广播地址分别发送 Wi-Fi MAC 对应的标准 magic packet，使用 UDP 9 和 7 各三次。115 秒观察窗口内未看到端口恢复，最终 ADB 仍 offline。恢复闹钟也未带来可观察的网络恢复；由于当时无法读回应用日志，不能确定闹钟是否执行或面板是否亮起。

结论限定：本次环境中单播与广播 WOL 均未实现可观察的恢复；不能据此断言电视硬件不支持 Wake-on-WLAN。尚需从电视所在网段发包，排除广播路由限制。当前没有可调用的米家授权，用户已验证的米家开机能力尚不能由 LIRA 直接执行。

本轮未修改 wifi_sleep_policy（读值为 0）或系统 ADB 属性。尚未复测将 Wi-Fi 休眠策略设为保持连接的效果，也没有证实 sys.set_adb_disabled 属性的含义；不能将这些读值作为已定位的根因。

已请求用户通过米家开机，暂不切换 ADB 调试以保留故障现场。待恢复后，使用仅发送 CNXN、只记录响应类型与长度的握手探针区分连接不可达、握手无响应和授权阶段问题。临时应用的闹钟需在恢复后取消，日志取回后停止服务并卸载；当前由于电视不可达，清理尚未完成。日常免手动操作目标尚未达成。用户随后反馈本轮米家也无法打开电视；再次检查 5555 与 6095 均连接超时，尚未进入 ADB 握手阶段。本轮故障不能仅归类为 ADB 恢复问题；是否为电视休眠、网络离线、系统异常或其他原因仍未确定。需先用实体遥控器恢复并确认屏幕状态，暂停进一步待机测试。临时应用清理仍待电视恢复连接后完成。 用户随后用实体遥控器开机，确认屏幕正常，未切换 ADB 开关。复查 6095 返回 HTTP 200；5555 的 TCP 连接成功，但发送 ADB CNXN 后四秒内没有收到协议响应。标准 adb connect 在八秒内超时，devices 显示 offline，shell 无法执行。由此将故障缩小到 TCP 建连之后的 ADB 协议交互阶段，尚不能区分电视 adbd 异常与网络路径对该交互的影响，不能认定为授权失败。诊断日志仍无法读回；下一步需再次切换电视 ADB 开关恢复访问，以便收集日志并清理临时应用，不再重复待机。
