# 摄像头官方栈对照验证与 3A 引入(A→B 分步)

## Summary

用零依赖的官方基准对照(阶段 A)先回答"自研采集路径是否正确使用了摄像头",再尝试安装官方 3A 栈 camera_engine_rkaiq(阶段 B)拿最佳画质;B 阶段画质对比明显优于现状才切换,否则保持现有软件 3A 路径为兜底,失败原因落档即收工。

---

## Problem Frame

M3 bring-up 以来,摄像头采集一直是自研路径:ISP mainpath 单帧 NV12 → 软件 3A(自适应模拟增益 + 数字曝光补偿 + 灰世界白平衡)→ 三帧择优。功能上可用,但开发者对其正确性始终没有外部参照——"不确定是否正确使用了摄像头"。同一块板、同一颗传感器,Orange Pi 官方文档展示的 Android 系统里摄像头开箱即用且画质良好,差异的来源是 Android 跑着 Rockchip 官方闭源 3A 守护进程(rkaiq/ispserver)+ 传感器 IQ 标定文件,而官方 Debian 镜像不带、此前调研结论为无公开 deb。

传输层已排除嫌疑:传感器 4224 宽被 rkcif 驱动因 MIPI 带宽/时序约束静默钳到 2688,是 `camera_raw.py` 已实测记录的已知约束,不是用法错误。真正没对照过的是画质处理层(3A/IQ)。

外部调研确认:官方 3A 栈在 RK3588 Debian 生态存在且厂商有打包(Radxa、FriendlyELEC 仓库提供 camera_engine_rkaiq 包;ubuntu-rockchip/Armbian 生态同样在用),但社区也报告过 5B 机型 ISP 问题与 OV13850 需补文件修复的先例——"装上就通"不保证,内核兼容性是主要风险。现有软件 3A 路径已实测可用,失败损失可控,适合分步走。

---

## Actors

- A1. 开发者(设备维护者):本工作的执行者;板上验证对照与官方栈引入均由其执行,结论落档服务于后续调参与阅读管线画质评估
- A2. 老人用户(设备旁):不参与本工作;唯一关联是若 B 阶段切换主路径,阅读拍摄画质随之变化

---

## Key Flows

- F1. 阶段 A — 官方基准对照验证
  - **Trigger:** 开发者开始摄像头画质工作,需要先钉死"用法是否正确"
  - **Actors:** A1
  - **Steps:** 链路/格式/传感器能力核对 → 镜像源 rkaiq 相关包查证(只查证不安装) → 同场景抓"驱动原生输出(无 3A)"与现管线输出并留存 → 对比分析(画质差异描述) → 结论落档
  - **Outcome:** "是否正确使用了摄像头"有明确证据结论;是否进入 B 有依据
  - **Covered by:** R1, R2, R3
  - **Failure/escape path:** 若对照全部通过且无画质异常,即结论"用法正确",B 仍可继续(追求画质上限)或按需跳过;若发现真错误,先修正再评估是否继续
- F2. 阶段 B — 官方 3A 栈引入(带回退)
  - **Trigger:** A 阶段结论支持继续,或直接追求画质上限
  - **Actors:** A1
  - **Steps:** 按来源顺序获取官方栈(Orange Pi 官方渠道 → 其他 RK3588 厂商包 → Rockchip SDK 二进制,按内核兼容性筛选) → 安装并配 IQ 文件 → 同场景与现管线对比 → 明显更优才切换主路径;否则回退
  - **Outcome:** 主路径为画质更优者;失败原因(内核不匹配/IQ 文件缺失等)落档
  - **Covered by:** R4, R5, R6, R7, R8
  - **Failure/escape path:** 不可适配(如内核不匹配)时,记录原因即收工,**不为 rkaiq 换内核/换镜像**;现有软件 3A 路径始终是可用兜底

---

## Requirements

**阶段 A — 官方基准对照验证**
- R1. 同场景参照抓帧:板上用参考工具抓取"驱动原生输出"(不施加自研 3A 后处理)的帧,与现管线输出同场景、同留存,作为画质对比基准
- R2. 用法核对清单:核对媒体链路拓扑、传感器支持格式/分辨率与当前采集配置一致;并查证镜像源/已装包中是否存在官方 3A 相关组件(复查此前"无公开 deb"结论,只查证不安装)
- R3. 对照结论落档:验证结论(用对了/哪里没对/画质差异描述)写入部署文档,作为 B 阶段决策依据

**阶段 B — 官方 3A 栈引入**
- R4. 来源顺序:按 Orange Pi 官方渠道 → 其他 RK3588 厂商包(Radxa/FriendlyELEC 等) → Rockchip SDK 二进制的顺序尝试获取,按内核兼容性筛选
- R5. IQ 文件:配齐与传感器(OV13855)匹配的 IQ 文件;无现成文件时以 OV13850 的起步并如实记录
- R6. 控制权让渡:官方栈生效时,自研路径停止直接控制传感器曝光/增益,避免双重控制
- R7. 切换判据:同场景对比画质明显优于现状才切换主路径;否则回退,现有软件 3A 保持主路径
- R8. 失败落档:不可适配时记录具体原因(内核不匹配/包依赖冲突等),现状即终态

---

## Acceptance Examples

- AE1. **Covers R1, R3.** Given 同一物理场景,when 分别抓取驱动原生输出帧与现管线输出帧并对比,then 差异可归因于自研 3A 处理,且对比材料与结论在部署文档可查。
- AE2. **Covers R2.** Given 镜像源与已装包,when 查证官方 3A 相关组件,then 得到"存在(给出包名)/不存在"的明确查证记录,不发生任何安装动作。
- AE3. **Covers R6.** Given 官方 3A 栈已生效,when 现有采集代码执行拍摄,then 传感器曝光/增益控制权归官方栈,自研路径不再写入这些控制项。
- AE4. **Covers R7.** Given 官方栈安装成功,when 同场景对比完成,then 画质明显更优才切换主路径,否则现有软件 3A 路径继续为主路径且无需改动。
- AE5. **Covers R8.** Given 内核不匹配等不可适配因素,when 安装尝试失败,then 失败原因落档,系统保持现状,不为 rkaiq 换内核/换镜像。

---

## Success Criteria

- "是否正确使用了摄像头"有明确证据结论(阶段 A 落档),不再依赖"功能上能出图"的间接推断
- 画质上限有实证答案:要么官方栈落地且同场景对比更优,要么失败原因明确落档、现状被确认为当前约束下的合理终态
- 全程不引入不可回退变更:主路径切换/回退均以对比证据为依据,现管线的可用性不受影响

---

## Scope Boundaries

- 实时视频查看(控制台 MJPEG 预览、GStreamer 实时管线):本轮不做;B 失败后若需要远程查看,可另行以现成管线立项
- 为适配 rkaiq 而升级/更换内核或系统镜像:不做,不可适配即落档收工
- 阅读流程/OCR 管线改动:不动;本轮只影响采集画质
- 面向家人的日常相机 UI、阅读确认环:不做
- IQ 文件的专业调优(tuning 服务):只做"配齐能用",不做深度调优

---

## Key Decisions

- **A→B 分步而非直接装官方栈**:先零依赖验证钉死"用法正确性",B 的画质判断才有干净基准;B 失败损失可控(现有软件 3A 已实测可用)(用户确认)
- **"明显更优才切换"判据**:官方栈不是默认正确答案;对比证据决定主路径,软件 3A 始终保留为兜底(用户确认)
- **不为 rkaiq 换内核/换镜像**:官方栈是"尝试引入"而非"必达目标";系统形态(官方 OPi Debian 镜像)不动摇(用户确认)
- **控制权让渡而非共存**:官方栈生效时自研路径不写传感器控制项,双重控制会让两套 3A 互相干扰、对比失效
- **只查证不安装(阶段 A 的 R2)**:镜像源复查只产出查证记录,避免验证阶段污染系统状态

---

## Dependencies / Assumptions

- 官方栈为闭源用户态守护进程,与内核 rkisp 驱动版本需匹配;Orange Pi 官方 Debian 镜像此前结论为不带 rkaiq 且无公开 deb——A 阶段 R2 将复查,该结论可能被推翻
- 传感器实到为 OV13855(采购清单为 OV13850);IQ 文件 availability 按此现实处理(R5)
- 外部先例:ubuntu-rockchip 报告过 5B ISP 问题、Armbian 报告过 OV13850 需补文件修复——引入存在不确定性,已以"失败落档即收工"的边界覆盖
- 现有软件 3A 路径(camera_isp.py)已板上实测可用,是全程兜底
- 对比实验的"明显更优"判定为开发者主观 + 基本客观指标(亮度分布/锐度)综合,不引入专门评分工具
