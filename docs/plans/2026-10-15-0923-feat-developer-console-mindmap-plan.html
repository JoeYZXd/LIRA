LIRA小丽拉的
调试小屋

配置看磁贴

交互看过程

  • A温馨卡通视觉用户要求

    小丽拉的调试小屋：温柔、清楚、有一点玩具感。

    • A1奶油色与清晰文字建议

      奶油白底色，杏桃橙主色，鼠尾草绿与淡紫分区，深棕文字。浅色不等于低对比度。

    • A2软陶磁贴建议

      圆角、轻阴影、统一手绘感矢量图标；卡通气质与精确数值共存。

    • A3柔和动效建议

      点击轻压、状态平滑过渡；支持减少动态效果。

    • A4可选 3D 小丽拉建议

      随聆听、思考、播报改变姿态；3D 只是点缀，可关闭并降级为静态形象。

  • B磁贴工作台用户要求

    配置按功能归属；先看状态摘要，点击再设置。

    • B1首屏概览建议

      设备连接、隐私模式、当前会话阶段、关键异常。

    • B2磁贴摘要建议

      功能名称、配置摘要、运行状态、异常数量。

    • B3点击展开设置建议

      常用参数优先，高级参数折叠；标明是否立即生效或需要重启，保留保存反馈与字段错误。

    • B4展开方式待讨论

      建议普通设置原位展开，复杂调试进入专属工作区；保持实时状态可见。具体布局待讨论。

  • C实时声音观察用户要求

    以设备真实麦克风数据展示连续曲线，联动激活与识别状态。

    • C1连续声音曲线建议

      显示输入能量、噪声参考、输入过小或削波提示；设备麦克风与浏览器麦克风明确区分。

    • C2声音与激活分层建议

      有声音 → 检测到人声 → 唤醒成功 → 接收指令。声音存在不等于唤醒成功。

    • C3时间轴标记建议

      标记唤醒、语音起止、播报与打断，可定位对应会话轮次。

    • C4输入参数建议

      展示输入设备与采集状态；仅把已支持的参数做成可调控件。

    • C5无数据与断连建议

      等待、断连、最后更新时间必须明确；不以装饰波纹冒充真实声音。

  • D大模型实时交互用户要求

    激活后即可看到当前轮次走到了哪一步。

    • D1语音会话联动建议

      展示识别中和最终文本，明确本轮是否实际调用大模型。

    • D2交互阶段建议

      等待识别 → 请求发送 → 等待首段 → 生成回复 → 播报 → 完成；标明失败、取消和打断。

    • D3真实回复流建议

      有流式数据时逐段展示；无流式能力时显示等待，不模拟生成过程。

    • D4耗时与路径建议

      识别耗时、模型首段与总耗时、播报启动耗时；显示当前模型与本地或远程路径。

    • D5同轮关联建议

      曲线、识别与回复属于同一轮；本地家电指令显示实际分支，上一轮回复不会混入下一轮。

  • E声纹小档案已确认

    日常交谈中自动积累多个候选声音；不是要求家人逐一进入录入向导。

    • E1总览：人数与名单用户要求

      分别显示已建立人数、积累中候选数、待关联身份数；已建立列表显示具体姓名。候选数不直接等同于真实人数。

    • E2已建立成员建议

      姓名、头像、声纹状态及家庭成员关联；已有身份不因相同姓名而自动覆盖。

    • E3自动积累候选声音已确认

      在正常交谈中接收有效片段，持续积累；同一候选跨多轮关联，不要求专门朗读固定内容。

      • E3a多个候选并存建议

        多个声音可分别处于积累中；尚未确认身份时使用“待认识的声音 01”等临时称呼。

      • E3b候选不等于人数建议

        同一个人的不同声音条件可能形成多个候选；不得直接宣称新增了一个家庭成员。

      • E3c异常与混合声音建议

        噪声过大、多人重叠、有效片段不足时说明原因，不强行推进进度。

    • E4真实的百分比进度建议

      百分比只表示满足已定义采集条件的进度；身份确认与匹配置信度另外显示。达成采集条件不代表身份已确认。

      • E4a进度依据建议

        建议结合有效语音片段、有效时长、声音一致性与质量门槛。具体完成条件留给规划与验证，不编造数字。

      • E4b停滞可解释建议

        显示“还需要清晰语音”等原因；证据不足时不随时间自动增长。

      • E4c建立过程建议

        建议阶段：发现声音 → 积累样本 → 声音档案就绪 → 等待确认姓名 → 已关联成员。

    • E5建立方向已确定已确认

      系统在日常交谈中自动积累。用户在“日常自动积累”与“选人后引导录入”之间选择前者。

    • E6姓名如何确认已确认假设

      已按用户确认的假设：日常交谈自动积累声音；自然对话确认称呼后再关联身份。新候选不自动绑定已有成员，同名关联须在已鉴权控制台确认；确认前不读取个人记忆。已建立声纹的正常识别继续保留。

    • E7现有能力与扩展边界代码事实

      现有代码已有声纹登记、匹配及单个 pending 对象；多人候选积累和可验证百分比属于新增能力。声纹向量已有本地存储，原始录音不因此自动留存。

  • F独立日志工作区用户要求

    实时声音、大模型交互与事件日志分别承载不同观察任务。

    • F1语音事件建议

      唤醒、识别、状态迁移、播报与打断；按轮次查看。

    • F2模型交互记录建议

      请求与回复时间线，可与实时模型模块互相定位。

    • F3系统运行日志建议

      设备事件、错误、耗时与日志级别。

    • F4阅读控制建议

      暂停自动滚动，按模块或异常筛选，清空当前展示。

    • F5内容边界建议

      调试识别文本和回复沿用内存展示通道，系统日志保持内容不落盘；内容导出另行讨论。

  • G其他功能磁贴建议

    保留已有测试能力，按功能收纳。

    • G1语音输出建议

      TTS 测试、音量、语速、录音回放。

    • G2视觉调试建议

      单帧拍摄、预览、OCR 结果与阶段耗时。

    • G3设备与同步建议

      连接与同步状态、手动同步及结果。

    • G4整机场景建议

      唤醒与指令回放、状态迁移观察。

    • G5运行配置建议

      参数按所属功能归类；明确配置来源和生效条件。

  • H使用底线建议

    温馨外观下保持真实、清晰的调试行为。

    • H1鉴权与隐私建议

      延续开发者鉴权；隐私模式开启时停止受限采集，候选积累显示暂停原因。

    • H2语音链路连续建议

      实时观察不抢占正常语音链路；关闭页面释放调试订阅。

    • H3可访问性与适配建议

      键盘可操作、焦点清晰、支持减少动态效果；小屏单列、大屏多列。

  • I建议推进顺序建议

    这是讨论中的顺序建议，并非实施排期。

    • I1磁贴与视觉建议

      建立信息结构与温馨视觉。

    • I2真实声音观察建议

      接入声音曲线和激活状态。

    • I3按轮次联动模型建议

      串联识别、模型与播报反馈。

    • I4声纹可观察性与扩展建议

      展示现有档案，再补多候选自动积累及真实进度。

    • I5趣味细节建议

      在基本能力清晰稳定后加入可选 3D。

Goal Capsule

Objective：开发者可以一边观察真实声音、交互轮次和成员声纹积累，一边在温馨清晰的控制台中找到并调整对应功能。

Means：功能磁贴、共享输入上的结构化观测、多候选声纹和独立日志工作区（KTD1–KTD6）。

Authority：用户最新答复 → 本文 Product Contract → Planning Contract 与开发单元 → 现有代码模式。A–I 为产品脑图索引；本文为同一路径的实施计划。

Stop conditions：若实现需要绕过隐私、收集未与 LIRA 交互的环境对话、自动覆盖已有身份、保存原始录音或改变现有家电确认规则，停止并提出范围问题。

Execution profile：8 个依赖有序的代码开发单元；先为跨层行为建立特征化/回归覆盖，再改运行路径。PR、提交和发布遵循后续执行指令；本次仅规划，没有实施、执行测试或部署。

Product Contract

Summary

把现有控制台改为功能磁贴，持续展示设备声音与同轮交互过程，新增多候选声纹自动积累和真实进度。复用当前服务、鉴权与诊断接口，保持温馨家庭助手风格。

Problem Frame

现有控制台将运行参数、测试与日志平铺；音频状态主要是每秒一条文本统计，模型展示缺少轮次标识，声纹只维护一个待确认对象。开发者难以连续判断“是否收到了声音、为什么被激活、这一轮模型做了什么、哪些人的声音已记住”。

Product Contract preservation：R1–R6、R9 语义保留并补齐对应脑图细节；新增 R10 记录用户确认的 E6 假设，R11 汇总既有功能保留要求。已移出的 R7/R8 脑图工具要求不属于 LIRA 实施范围，不复用其编号。

Key Decisions

日常交谈自动积累，取代专门引导录入。Governs R4, R5。（session-settled: user-directed — chosen over guided enrollment: 用户明确选择日常交谈自动积累。）

采用确认后关联身份的保守假设。Governs R10。（session-settled: user-approved — chosen over automatic binding: 用户确认自然对话确认称呼、同名须控制台确认，防止错用成员记忆。）

Actors

A1. 已鉴权开发者：配置、观察和确认同名身份关联。

A2. 与 LIRA 交谈的家人：在自然交谈中积累声音。

A3. 设备运行时与模型服务：提供真实状态和回复，不由页面制造事件。

Key Flows

F1. 日常交谈 → 发现/命中候选声音 → 积累有效证据 → 显示阶段和采集进度 → 确认称呼 → 按 R10 关联成员（R4、R5、R10）。已有声纹的可靠匹配继续按现有身份识别工作。

F3. 收到处理后设备声音 → 人声/唤醒标记 → 临时识别 → 最终识别与实际路由 → 若实际调用模型则显示回复 → 播报完成或中断（R2、R3）。

Acceptance Examples

AE2. Covers R4, R5：A/B/A 交替交谈后仍保留两个稳定候选，A 的有效证据累加；噪声或重复片段不虚增进度，候选不冒充家庭成员。

AE3. Covers R2, R3：无声音数据、麦克风暂停或模型断连时显示真实状态；上一轮迟到回复不进入新一轮，本地家电指令不显示假模型进度。

AE4. Covers R10：声音称呼与已有“妈妈”同名时只生成待确认关联；已鉴权控制台确认前，不读取妈妈的记忆，也不覆盖妈妈既有声纹。

AE5. Covers R9：隐私开启或口令轮换后，打开的观察页停止获取受限数据；隐私前尚未提交的异步声纹结果不得落库。

AE6. Covers R1, R6, R11：开发者从磁贴进入原有录音、TTS、相机方向、OCR、同步和场景回放；窄屏可操作，减少动态效果开启时信息完整。

Scope Boundaries

覆盖 A–I 的产品能力；不引入独立控制台服务或新端口，不改首页文字聊天的选人方式，不扩展家电权限，也不引入常驻环境对话采集、远程音视频监听、原始录音存储、人物数量识别承诺或持续说话人分离系统。脑图钢笔、保存服务和全局 skill 是协作工具，不进入实现单元。

Deferred to Follow-Up Work

完整模型连接信息编辑、任意 config.yaml 在线写入、声纹人工合并/替换/重建管理、文本内容导出、完整频谱分析、跨设备声纹同步均不纳入本计划。可选 3D 的具体形象可在 U8 内做轻量设计，不为此延迟核心验收。

Dependencies / Assumptions

自动积累解释为与 LIRA 主动互动期间的有效语音；这是结合既有隐私和会话路径的范围假设。设备已有可用的说话人模型和音频链路；模型缺失时对应磁贴显示不可用，不影响其他功能。

新增候选数据只存本地向量、质量与进度元数据，不存原始音频。新名称通过自然对话确认后才创建/关联成员；同名已有成员仅在鉴权控制台确认，已有声纹不覆盖。

Outstanding Questions

Resolve Before Planning：E6 已由用户确认，无剩余阻塞产品问题。

Deferred to Implementation：板端音频质量阈值和样本目标的校准值、最终图标与 3D 形象；必须通过 U8 的验收门槛，不能以未经校准的分数宣称识别准确率。

Planning Contract

Product Contract 决定行为，以下决策限定实现方式；具体函数命名与 SQL 留给执行阶段。

Key Technical Decisions

KTD1. 延用单服务和现有模板体系

把 dev.py 的大 HTML 字符串拆为开发者专用 Jinja 模板及本地 CSS/JS；保持 FastAPI 挂载、签名会话、现有测试端点。复用无前端构建链模式，不引入 React 或额外端口。静态资源和模板显式加入 wheel 包数据。

Basis：R1、R6、R9、R11；ui/app.py 的 Jinja 初始化与 mount_dev

KTD2. 被动音频遥测与文本事件分开存储

在 PrivacyGatedSink 之后的 RouteDispatch.feed 旁路计算每 100ms 的 min/max 小包、RMS、峰值、削波比例；观察不打开第二个音频流。音频环保留最近 10 秒，文本事件单独限制 500 条及总字节 512KiB。无观察者时跳过波形摘要计算，日常声纹积累不依赖页面开启。

Basis：R2、R9；main._orchestrate、RouteDispatch.feed、DevHandle.start_recording 的独占麦克风事实

KTD3. 显式轮次与操作映射

事件包含 runtime_instance_id、递增 seq、单调采集时间、capture_generation、utterance_id、turn_id 及可选 operation_owner。唤醒仅开聆听上下文，接收有效语句形成 utterance，状态机接受该语句后分配 turn；一次 turn 可以关联多个 operation，不能把 operation_id 直接当 turn_id。新轮次不能接受旧 generation/owner 的事件。

Basis：R3；RouteDispatch.generation 与 DialogEngine.OperationOwner

KTD4. 先采用有游标的短轮询

新增一个聚合观察端点返回音频窗口、事件增量及最新状态，默认可见观察页每 250ms 拉取且最多一个在途请求；声音每 100ms 摘要由页面插值绘制，标明为包络而非完整 PCM。后台页面和未展开实时区停订阅，失败按 1/2/4/8 秒退避。每次请求复用会话校验，401 停止，隐私 403 清除当前敏感展示。

Basis：R2、R3、R9；现有 JSON/fetch 路径。暂不引入 SSE，以避免长连接会话失效处理与逐卡连接数问题；若以后采用，仅用每页单连接。

KTD5. 候选证据可持久化，进度有版本

增加与成员分离的候选表，保存稳定 candidate_id、聚合向量、模型指纹/维度、不同 utterance 的有效计数/时长、质量统计、采集策略版本及状态。初始可校准目标为至少 3 段独立合格语音且累计 10 秒；每段至少 1 秒，去重且通过能量/削波及向量一致性门槛。采集进度取计数和时长完成比例的较小值，未过一致性门槛最多 99%；条件齐备才为 100% 且仍可显示待身份确认。

Basis：R4、R5；personal_memory.py 当前只保存成员向量且 pending 单一。3 段/10 秒为工程初值，不代表识别准确率；U8 校准不合格不得发布 100% 就绪承诺。

KTD6. 身份确认和记忆授权分别受门控

用 candidate_id 关联当前自然命名上下文；声纹积累不创建家庭成员。新称呼明确确认后才晋升；同名候选走开发者鉴权 POST 确认且事务复核成员与声纹，已有 profile 不替换。确认前 voice_member_id 为 None，个人记忆读写保持关闭；已建立 profile 的可靠匹配不要求每轮重新命名。

Basis：R10；Governs R10 的用户批准方案。personality 提示不得绕过 member_id/隐私边界。

KTD7. 模型显示观察器与 TTS 回调隔离

为普通流式和搜索代理路径提供只读观察事件，观测实际请求、首个非空内容 delta、后续文本、完成/失败/取消；不复用句级播放回调驱动 UI。voice_log=False 的首页文字聊天保持不向语音调试通道发送内容，用户可见回复不包含隐藏推理或系统提示。

Basis：R3、R9；LlmClient._stream_chat、_search_chat 与 on_reply_chunk 的当前差异

KTD8. 渐进上线与本地资源

先使原测试入口在新外观可用，再接观察与声纹。候选表采用幂等新增；已有 members/voice_profiles 不迁移或覆盖。新代码关闭时旧流程仍能运行。可选 Three.js 仅本地固定版本随包交付、按需加载且有静态回退；若维护成本不合适则用 CSS/SVG 温柔动效。

Basis：R6、R9、R11；当前 pyproject.toml 的 UI 包数据缺口

High-Level Technical Design

音频数据沿现有唯一输入进入隐私门，之后同时供识别和轻量观测；遥测只保留摘要，不向浏览器传 PCM。事件由识别、路由、模型与播报生产，经有界存储和鉴权接口投射为页面状态。

Assumptions and Limits

  • 新候选不代表新的人。相似向量接近两个已有候选时拒绝计入并显示“声音归属不明确”；不声称解决完整多人重叠分离。
  • 质量门槛初值、保留上限与发布门槛属于可验证工程参数。值在策略版本中记录；改变时重新计算或明确要求重新采集，不能静默把旧证据变成新 100%。
  • 候选积累仅在隐私允许的 LISTENING/FOLLOWUP 有效交谈中进行；没有新声纹模型时显示不可用，不自动下载模型或上传音频。
  • 现有未提交工作是研究基线。实施前保护用户工作，不把本计划当作允许提交/发布全部脏文件的授权。

System-Wide Impact

实时链路新增观察不能产生反压：生成摘要超预算时可丢弃旧图形样本并发 gap，不能阻塞音频处理。文本分片按小批合并写入有界缓冲，但保留首段到达时间，完成事件携带完整受限长度回复快照供追赶。重启使 instance_id 变化；旧页面收到 reset 后清空上下文。

隐私切换、取消和关机均必须让未完成的 embedding/模型结果在提交前重新检查 owner/generation/隐私。提取工作在线程中计算，SQLite 写入回到运行时事件循环串行执行。身份确认 API 与语音晋升使用同一领域操作及事务，模型不能自行确认同名身份，页面也不能通过通用参数写入接口绕过它。

Risks, Rollout and Recovery

  • 板端双流会饿死原采集：只做共享输入旁路，独占录音沿原路径；U8 对比开关观测前的捕获间断。
  • 家庭声音差异与环境噪声使初始门槛不可靠：拒绝质量不足片段并显示原因，校准前不发布准确率宣称。
  • 持久化候选与旧程序共用数据库：新增独立表，升级前备份，旧表不做破坏性迁移；回滚关闭新功能并保留新增表，不删除家庭历史。
  • 无 SDK delta 或终端故障：真实显示等待/失败，页面不能补出伪回复；展示订阅断开不应取消正在服务用户的正常对话。
  • 新增 UI 资产漏打包或依赖 CDN：wheel 安装与离线浏览必须纳入 U8，不以源码目录打开成功替代发布包可用。

Implementation Units

按依赖推进，不把 UI 美化与真实采集能力混为一项。U1 与 U2 可分别建立；U6 在 U2 后可与 U3–U5 并行设计，最终由 U7/U8 汇合。

Approach

  2. 从主对话已有有效语音提取 embedding，保持异步 owner/generation/隐私检查，提取后提交前再次验证；不额外采集环境对话。
  3. 记录有效段/时长、拒绝原因及策略版本；实现有界候选/去重缓存和过期，不存原音频；相似度不是百分比。
  4. 模型指纹或维度变化时不混合向量；显示需要重新积累，旧成员 profile 的兼容性也需明确检查。
Execution note

板端交付门槛

  • 固定同一音频场景对比观察关闭/开启两种状态，连续运行至少 10 分钟：不出现观测导致的第二采集流、额外音频断档或 TTS 重复；记录处理时延和 CPU/内存变化，若主音频线程超过其 100ms 块周期则失败。
  • 观察页的数据到图形显示延迟以 p95 ≤1 秒为目标；250ms 拉取最多一个在途请求。负载下可丢图形旧包并标 gap，不能让主语音业务排队等待页面。
  • 遥测文本内存 ≤512KiB 且 ≤500 条，音频包络只保留最近 10 秒；关闭/隐藏所有观察页后不再产生该页面订阅任务，候选积累仍随正常交谈工作。
  • 隐私开启后，新的受限样本、文本和候选写入立即停止；已打开页面下一次成功拉取在 1 秒内清除展示。网络不可达时以断线状态显示，不能声称仍是实时数据。
  • 校准记录必须包含不同候选交替、相似声音、低质量/重叠可疑输入、重启恢复与同名确认。未通过的候选不显示就绪 100%；不将收集完成度宣称为身份准确率。
